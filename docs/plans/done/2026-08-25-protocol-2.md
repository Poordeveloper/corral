# Protocol 2 — a version for a request contract that changed

Founder-accepted 2026-08-25:
`docs/decisions/2026-08-25-protocol-2-acceptance.md`. The decision is settled;
this plans its implementation.

## Goal

```text
PROTOCOL_VERSION           = 2
MIN_COMPATIBLE_PEER_VERSION = 2
```

so that two peers which disagree about `session.new`'s request contract find
that out in the handshake, where the mechanism for saying so already exists,
instead of at the first request as a decoder error.

## The problem this closes

`session.new` gained a required `command_id`. Both a build before that change
and a build after it declare `protocol_version = 1`, so `compatible()` returns
true and the daemon answers a hello saying so. The disagreement then surfaces
one request later, as `invalid_params` carrying a serde message — after the
handshake already told the client it could rely on this daemon.

The hello is the place Corral says what it can talk to. A hello that says
"compatible" to a peer this build cannot serve is the hello being wrong, and no
amount of care further down repairs that.

## Non-goals

No capability negotiation for this. Capabilities answer *does this peer have
feature X* — an additive, optional ability whose absence means the peer simply
does not have it. `session.new`'s parameters are not an optional feature: the
same method means something different on either side. Expressing that as a
capability would leave every client maintaining a method-version matrix, a
capability gate and a fallback schema for one method, which is more complexity
than the version field exists to avoid.

No migration path for protocol 1 peers. There are none to migrate: this is the
correction of an unreleased contract, not the breaking of a published one.

No change to `session.new`'s shape. It is already what protocol 2 serves.

## Design

**1. The two constants move to 2**, in `corral-protocol`.

**2. `MIN_COMPATIBLE_PEER_VERSION`'s doc stops saying what it says now.**
Today it reads "Protocol 1 is the first version, so it is its own floor",
which is a fact about there being nothing older. The replacement states the
rule rather than this instance, and states explicitly that the floor is not
bound to the version:

> A version governs breaking change; capabilities govern additive evolution.
> The floor is the oldest peer this build can actually serve, which is not
> automatically the current version — a protocol 5 build whose every change
> since 3 was additive has a floor of 3.

It is 2 today because protocol 1's `session.new` is a request this build
cannot serve, not because floor tracks version.

**3. Every place that names "protocol 1" is corrected or made version-free.**
The survey:

| Where | Now | After |
|---|---|---|
| `corral-protocol/src/lib.rs` module doc | "only what protocol 1 actually serves: the bootstrap handshake, `ping`, and `session.list`" | protocol 2, and the real method set, which has since grown `session.new` and `terminal.attach` |
| `corral-protocol/src/method.rs` module doc | "The protocol 1 baseline" | protocol 2 |
| `corrald` `MethodNotFound` message | "this daemon speaks protocol 1" | built from `PROTOCOL_VERSION`, so it cannot go stale again |
| `corrald` no-params refusal | "takes no parameters in protocol 1" | built from `PROTOCOL_VERSION` |
| `corral-client/src/error.rs` doc | "idempotency semantics protocol 1 does not define" | protocol 2 now defines them for `session.new`; the wording is corrected rather than renumbered |
| `corral/tests/*` doc comments and one assertion | "protocol 1" | the assertion checks the version the build declares |

The two daemon messages are the point of that column: a hardcoded version in a
message is a second declaration of the same fact, and it is the one that goes
stale silently.

**4. `framing.rs`'s `MAX_FRAME_BYTES` comment** says "far above any legitimate
protocol 1 message". Left alone in substance — it is a statement about message
sizes, not about the version — but it names the version, so it says protocol 2.

## Interfaces or persistence changed

Wire: the version pair both peers declare. Nothing else — no method, no
parameter, no error code, no framing.

Persistence: none. No stored value carries a protocol version.

## Failure / unknown states

A protocol 1 peer meeting a protocol 2 daemon: the daemon answers the hello
with `Compatibility::Incompatible`, carrying both its own versions, then closes.
The client reports both sides and stops. That is the existing path, and it is
what the change exists to route this case into.

A protocol 2 client meeting a protocol 1 daemon: the same, decided on the
client's side, which already refuses to take a daemon's verdict on trust.

Nothing is retried and nothing degrades: an incompatible peer is terminal, and
the client never starts a replacement daemon over it (ADR 0001).

## Tests

- A peer declaring protocol 1 is refused at the handshake, with both version
  pairs stated, and never reaches a request. This is the regression: before
  the change it would be told it was compatible.
- The refusal is a hello verdict, not a decoder error — asserted on the
  answer's shape, so a future change that let a protocol 1 `session.new`
  through would fail here rather than in a message string.
- The existing compatibility matrix in `handshake.rs` moves to the new
  version pair and keeps proving both peers reach the same verdict.
- A daemon's `MethodNotFound` and no-params refusals state the version this
  build declares, so the two messages cannot drift from the constant again.

- `./scripts/verify` green on the final tree.

## What changed on contact with the code

**Two stale claims were corrected rather than renumbered.** `session.list`'s
comment and `vouch`'s doc both said "protocol 1 assigns no session encoding",
which stopped being true when PR3 gave the wire a session shape. Renumbering
them to 2 would have carried a false statement forward under a new number; they
say what is actually true now — the list is answered from the runtime, and the
store is asked because a list is a claim made in its name.

**The tests read the constants rather than the number.** `establish()`
documented itself as handshaking "at this build's own protocol version" and
then wrote `1`. Every version assertion in the suite now comes from
`corral_protocol`, so the next version change moves the suite with it instead
of leaving a row of assertions against a number the build no longer declares.

## Plan size justification

Small and single-purpose: one contract statement, its documentation, and the
tests that prove the handshake now carries it. The prose corrections travel
with it because they are the same statement written in six other places, and
leaving them saying "protocol 1" would leave the repository disagreeing with
its own wire.
