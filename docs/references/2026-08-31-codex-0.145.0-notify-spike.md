# Codex 0.145.0 notify spike — ADR 0009 acceptance prerequisite

> Exact-version runtime evidence for ADR 0009's load-bearing facts, ruled
> a prerequisite of acceptance by the PR6 grill
> (`docs/decisions/2026-08-31-pr6-codex-notify-grill.md` Q6). Public
> `codex-rs` source (notify defined as an optional argv array; JSON
> appended as one argument; `-c` above user/profile/project layers) is
> supporting evidence only; every claim below is from a run performed on
> this machine. PR6's merge-time matrix re-verifies against whatever
> ships then.

## Versions and method

| | |
|---|---|
| codex-cli | 0.145.0 (`codex --version`) |
| OS | macOS (Darwin 25.5.0) |
| Date | 2026-08-31 |
| Corral commit | a0316ee |
| Driving | interactive TUI (`codex`) in a tmux pane, one trivial turn per scenario |
| Capture | notify program = shell script recording its full argv, a 1 s stdin probe, cwd, and time |

The capture script's own first argument is its output path; anything
Codex appends follows it. Scenario 3 runs under a scratch `CODEX_HOME`
(auth copied, mode 0600, deleted after) so a user-level `notify` could be
configured without touching the real `~/.codex/config.toml` — the scratch
home was confirmed in effect before the turn ran (its
`model_reasoning_effort = "low"` visible in the TUI header; its
pre-seeded project trust honored).

## Scenario 1 — interactive TUI fires top-level notify: PASS

`codex -c 'notify=["<capture.sh>","<out>"]'`, one completed turn.
The notify program was invoked; payload `client` field reads
`"codex-tui"`. D1's primitive holds for the interactive TUI, not only
`codex exec` (S2's channel).

## Scenario 2 — payload is the final argv item, argv only: PASS

Exactly one argument was appended after the configured ones
(`argc_after_out=1`), holding the notification JSON verbatim; stdin gave
EOF immediately (no payload on stdin). Observed payload:

```json
{"type":"agent-turn-complete",
 "thread-id":"01a0576f-0ecc-7b21-9719-f38f9e4ef933",
 "turn-id":"01a05770-2763-74e0-a44c-e6156a0f8cc3",
 "cwd":"<run dir>","client":"codex-tui",
 "input-messages":["Reply with exactly: ok"],
 "last-assistant-message":"ok"}
```

Same shape as S2's `codex exec` capture; `client` differs
(`codex-tui` vs `codex_exec`). Identity (`thread-id`) present. On exit
the TUI prints `To continue this session, run codex resume <thread-id>`
— the D5 resume verb, stated by the provider itself.

## Scenario 3 — runtime `-c notify` wins over configured notify: PASS

Scratch `CODEX_HOME` with `notify = [<user capture>]` in `config.toml`,
launched with `-c 'notify=[<corral capture>]'`, one completed turn. The
scratch home was verified in effect first (its model effort and
pre-seeded trust visible in the TUI). The `-c` program fired; the
configured program stayed silent through a grace window. D4's override
strategy holds on this version.

## Scenario 4 — no persistent configuration residue from the override

After scenario 1's session exited, `~/.codex/config.toml` contained no
`notify` key and no other override residue. The file's bytes did change
— Codex persisted the answer to its own first-run directory-trust prompt
(`[projects."<run dir>"] trust_level = "trusted"`), a Codex-owned
behavior triggered by the interactive trust question, present with or
without Corral's flag. Ruled interpretation (grill Q1): the substitution
is process-local; the trust write is the user's own answer to the
provider's own question, and a managed launch in an untrusted directory
will surface that same question unchanged. A clean re-check rode
scenario 5's run in the already-trusted directory: no prompt appeared
and `config.toml` was byte-identical before and after — including after
declining the TUI's own update offer (0.145.0 → 0.151.0, skipped; the
merge-time matrix re-verifies against whatever is then installed).

## Scenario 5 — last `-c notify` wins among repeated flags: MEASURED

Two `-c notify=[…]` flags on one invocation, one completed turn: only
the **last** program fired; the first stayed silent. A caller's later
`-c notify` therefore displaces Corral's injection — the design-5
refusal of caller notify spellings is load-bearing, not defensive
ornament, exactly as Claude's repeated `--settings` was (PR5 matrix
scenario 8).

## Verdict

Scenarios 1–3 — the acceptance-gating facts of grill Q6 — all pass;
scenario 4 is clean on the re-check with the one attributed exception
(Codex persisting the user's own trust answer); scenario 5 seals the
refusal rationale. ADR 0009's load-bearing facts are measured on
codex-cli 0.145.0.
