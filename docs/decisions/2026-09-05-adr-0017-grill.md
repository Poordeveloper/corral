# ADR 0017 Grill — rulings over snapshot geometry, dual-screen state, and palette transport (round 1)

> Status: **closed** (2026-09-05). One round ruled the six structural
> questions; two correctness holes in the proposed text were closed by the
> rulings (Q2's budget order, Q3's send condition), and acceptance was made
> conditional on one factual check (Q5), which passed the same day. ADR
> 0017 moved `proposed → accepted` on the strength of this record without a
> second round, as Q6 allows. The implementation is a standalone
> high-consequence Class B PR that precedes PR9 planning.

Questions asked by the grill session of 2026-09-05; rulings verbatim below.

# Round 1

Digest of what round 1 froze:

| Q | Ruling |
|---|---|
| Q1 | D1 accepted with a snapshot-anchor semantic: `Geometry(E,N)`, `[Palette(E,N)]`, `Snapshot(E,N)` describe one recoverable state checkpoint; transport frame ordering is not weakened to say so. A new client on an old daemon may fall back to its last requested geometry but must not call it daemon-confirmed. A capability-advertising daemon that sends a Snapshot without its Geometry prefix has desynchronised the stream: do not install the Snapshot, request resync. |
| Q2 | D2 semantics accepted. Mechanism A conditionally: a formatting-only operation on the screen thread that emits no delta, advances no epoch or sequence, fires no callback, changes no observable screen/cursor/mode state, is invisible to other subscribers, and is guarded so a panic cannot leave the wrong screen active; else a bounded local adapter exposing the formatter, never a semantically mutating switch. **Budget corrected**: an alt-active successful snapshot may not omit the inactive main viewport; both current viewports plus the active-screen identity are required state; histories degrade first; if both viewports cannot fit under the ceiling the snapshot fails with a typed error and the daemon stays healthy. |
| Q3 | D3 accepted with the send condition replaced: `Palette` is a checkpoint of the effective palette at the snapshot point, compared against the checkpoint this connection is known to have received (baseline: default); sent when they differ, including custom → default, for which an explicit reset form exists. Compare semantic palette state, not formatter bytes. A resync never depends on an earlier palette delta having arrived. |
| Q4 | D4 accepted with Q3's correction: the prefix is `Geometry`, `[Palette if required]`, `Snapshot`, all at one snapshot state point; a resync yields the complete prefix even inside the same epoch; stale-epoch prefix members are discarded like a stale snapshot; a prefix member from one epoch is never combined with a snapshot from another. |
| Q5 | D5 accepted in principle: 7 and 8 permanently assigned now; daemon-side capabilities; no durable state. Acceptance prerequisite: prove the pre-ADR client decoder skips kinds 7 and 8 exactly, stays frame-synchronised, writes nothing to the terminal, does not disconnect — against the actual old decoder, not a fixture added to the new one. And the additions must stay additive: nothing an old client relies on leaves the legacy Snapshot without peer negotiation; record which case holds. |
| Q6 | (A) After the Q2/Q3 corrections and the Q5 check, the ADR flips to accepted without another round; then a standalone high-consequence Class B PR implements it — kinds, capabilities, geometry codec, palette checkpoint bookkeeping, dual-screen construction, complete resync prefix, the fidelity and channel tests listed — before PR9 planning. |

## The Q5 check (2026-09-05)

Run against the decoder as it stands on `main` at `38c75f8`, whose
terminal framing was last changed in `7182927` and whose TUI `apply` in
`c59299a`, both before ADR 0017 existed:

- `corral-protocol` `terminal::tests::the_geometry_and_palette_kinds_are_skipped_by_a_decoder_that_predates_them`:
  a kind-7 frame with a four-byte geometry payload and a kind-8 frame with
  OSC 4/10 text decode as `Unknown(7)` and `Unknown(8)`, are skippable,
  consume exactly their declared length, and the Snapshot after them
  decodes with the stream still frame-synchronised. **Passed.**
- `corral-tui` `attach::tests::geometry_and_palette_frames_write_nothing_and_the_snapshot_after_them_still_applies`:
  `apply` writes nothing for either kind and the following Snapshot still
  reaches the terminal; the attach loop treats an unknown kind as applied,
  not as an error, so no disconnect. **Passed.**
- Additivity: the legacy Snapshot is minted with `palette: false`
  (`runtime/snapshot.rs`), so no old client relies on palette state in the
  Snapshot; `Palette` (8) is purely additive. `Geometry` (7) carries nothing
  an old client had. No peer negotiation is needed for either.

Both tests stay in the tree as the permanent record of the property.

1. Q2 不能允许 alt-active snapshot 把 inactive main viewport 本身裁掉，否则以后收到 `?1049l` 时客户端没有东西可恢复。
2. Q3 不能规定"当前 palette 是 default 就不发 Palette"，因为同一连接可能之前是 custom palette、又漏掉了 reset delta，resync 后会继续拿旧颜色。

* Q1 = 接受，补一个 snapshot-anchor 语义
* Q2 = 语义接受、机制 A 有条件接受，但修改 budget degradation
* Q3 = 修改后接受：Palette 表达 effective palette checkpoint，包括回到 default

这里的：

如果现有 frame sequence 要求：

Q2 — dual-screen snapshot
接受 D2 的核心语义：
When alternate screen is active,
a recoverable snapshot must preserve both:

* the currently active alternate screen
* the inactive main screen that will become visible when the application
exits alternate-screen mode

and must establish which screen is active.
The ANSI reconstruction form may be conceptually:
main screen state
→ switch into alternate screen
→ alternate screen state
→ remaining accepted extras
Mechanism A
有条件接受：
temporarily expose/format the main screen on the authoritative screen thread
without waiting for an upstream qwertty release.
But this is allowed only as an implementation-local formatting operation.
It MUST NOT become an observable terminal state transition.
Specifically, temporary formatter access must not:

* emit a terminal delta
* advance terminal epoch
* advance semantic state sequence
* trigger resize/screen-change callbacks
* change externally visible active-screen state
* alter cursor/mode state after snapshot construction
* be observable by another subscriber

Required regression:
authoritative terminal state before snapshot construction
authoritative terminal state after snapshot construction
for all state dimensions owned by qwertty/Corral.
Use RAII/guarded restoration or equivalent fail-safe mechanism so an early
error/panic cannot leave the authoritative terminal on the wrong screen.
If qwertty's public screen-switch operation cannot satisfy this property,
do NOT force mechanism A through a semantically mutating switch.
Use a bounded local adapter/patch exposing the required formatter access.
Upstream exposure remains desirable follow-up,
not a correctness dependency.
Important budget correction
Reject this proposed degradation order:
trim main history
→ omit main screen itself
→ eventually trim alt
A successful alt-active Snapshot may NOT silently omit the inactive main
viewport.
Why:
snapshot arrives while alternate screen is active
→ client reconstructs alt
→ later normal delta contains `?1049l`
→ client must reveal the preserved main screen
If the snapshot omitted that main viewport,
the client cannot correctly process an otherwise valid future alt-exit
transition.
Therefore for an alt-active successful snapshot:
required current state includes:

* complete current main-screen viewport
* complete current alternate-screen viewport
* active-screen identity

Histories remain degradable.
Budget order:

1. trim oldest inactive/main-screen scrollback/history
2. trim other optional scrollback according to accepted snapshot policy
3. retain both current screen viewports

If the two required current-screen states together cannot fit beneath the
hard Snapshot safety ceiling:
→ explicit SnapshotTooLarge / equivalent typed failure
→ daemon remains healthy
→ no successful partial dual-screen snapshot
Do not claim successful recoverability while knowingly omitting the screen
that the next `?1049l` may expose.
Core invariant:
While alternate screen is active, both current screen viewports are part
of the recoverable terminal state; history is optional, the inactive main
viewport is not.

OSC 11

→ reset delta is lost / subscriber desynchronizes
→ resync happens

→ daemon omits Palette because it is default
→ replica retains stale custom palette
That violates the purpose of resync.
Correct rule

Default
For each Snapshot/resync bundle:
compare:
current effective palette state
against:
the palette checkpoint state this connection is known to have received
successfully
If they differ:
→ send Palette before Snapshot
This includes:
custom → different custom
and critically:
custom → default
Default must therefore have an explicit representable checkpoint/reset
form when required.
If:
connection baseline/default
+
current effective palette is default
→ Palette may be omitted.
If:
last checkpoint already equals current effective palette
→ Palette may be omitted.
Normal palette mutations between snapshots may continue through ordered
terminal deltas.
Palette frame exists specifically so a new attach/resync checkpoint is
self-consistent even when prior deltas cannot be trusted.
Compare semantic palette state,
not merely formatter output bytes,
unless formatter byte stability is itself part of the tested contract.
Core invariant:
A successful resync cannot depend on the client having received an earlier

Q5 — compatibility contract
大方向接受：

* frame id 7 permanently assigned to Geometry
* frame id 8 permanently assigned to Palette
* never reuse/reassign them
* no durable state
* capabilities advertised by daemon
* TUI may ignore supplemental frames it does not consume

Backward decoder capability check
Before flipping ADR 0017 to accepted, prove that the immediately preceding
compatible terminal client decoder already handles unknown framed terminal
message kinds safely.
Specifically an old-compatible client receiving:
type = 7
payload = arbitrary valid Geometry bytes
or:
type = 8
payload = valid Palette bytes
must:

* recognize it as an unknown framed message
* skip exactly that frame payload
* remain frame-synchronized
* NOT write the payload as terminal ANSI/data
* NOT disconnect merely because the frame type is unknown

This should be demonstrated against the actual pre-ADR decoder behavior,
not merely by adding an `Unknown(7)` fixture to the new decoder today.
Why:
future-input compatibility protects:
today's client against tomorrow's frame
but cannot retroactively teach an older binary how to parse today's new
frame.
If the check passes
Daemon-only capabilities are sufficient for these additive frames.
Old clients:
→ safely skip Geometry/Palette
→ retain their prior fidelity behavior
New clients:
→ use daemon capabilities to require the new snapshot prefix semantics.
If the check fails
Then daemon-only capability negotiation is insufficient.
One of these is required before implementation:

* client advertises terminal.geometry.v1 / terminal.palette.v1 support; or
* minimum compatible protocol version changes; or
* another explicit compatibility projection

Do not simply send frame 7/8 to a decoder that cannot safely skip them.
Additional compatibility constraint
ADR 0017 additions must remain additive for old clients.
Do not remove information from the legacy Snapshot payload that old
clients currently require unless the daemon can establish that the peer
supports the replacement frame.
For example:
if legacy Snapshot currently embeds palette state that old clients depend
on,
moving that state exclusively to Palette=8 requires peer capability
negotiation.
If legacy Snapshot already omitted that state,
Palette=8 is purely additive and old behavior is unchanged.
Record which case is true as part of the compatibility check.
Core invariant:
Unknown-frame tolerance must be a property the older decoder already had;
new tests cannot manufacture backward compatibility after the fact.
